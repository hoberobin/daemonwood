# Ralph loops — v0.13 the trust audit

One question for the whole pass: *can the map be trusted the way the terminals
can?* Every finding below was checked against the running machine — the
bridge's own health log, Claude Code's files on disk, the strings in the
Claude Code binary, and hook payloads captured from a live session — not
against what the documentation said was true.

## Loop 1 — Where do the hooks actually go?

**Finding:** `npm run connect` wrote the "every project" install to
`~/.claude/settings.local.json`. Claude Code reads exactly three settings
files for hooks, and the binary names them: `~/.claude/settings.json`, a
project's `.claude/settings.json`, and a project's `.claude/settings.local.json`.
There is no user-level `settings.local.json`. Two interactive sessions were
running on the author's machine all day and never reached the map; the only
session that did was in this repo, which had a project-local install. `npm run
status` reported everything connected.

**Change:** The user-wide install goes in `~/.claude/settings.json`, the file
the status line already lived in. Connect and disconnect both strip anything
of ours out of the old file and say so. A project install still goes in that
project's `settings.local.json`. Disconnecting one project no longer unwraps
the user-wide status line.

## Loop 2 — Refused for arriving early

**Finding:** The second proof of a session was its transcript, and a
transcript appears at the first prompt — the author's session opened at
11:08:42 and its transcript was born at 11:10:01. `SessionStart` and
`UserPromptSubmit` both fire before that (captured live: `transcript=false`
on both), so every new session's first events were refused with "Claude Code
has no session", the refusal chip lit for five minutes on every session
start, and the health log had the author's own session as its last refusal.

**Change:** Claude Code writes a note per running process,
`~/.claude/sessions/<pid>.json`, the second the process starts, naming the
session it hosts. That note is the proof now. It is checked against `ps` by
start time so a note left by a dead process can never speak for whoever
inherits its pid. The transcript ledger is the fallback for a process with no
usable note, and nothing else.

## Loop 3 — `/clear`

**Finding:** `/clear` keeps the process and gives the terminal a new session
id. The rule "one pid, one session" then refused every event from the new
session as an impostor, forever, while the old session stood on the map as
Done for the rest of the day.

**Change:** The note names the session the process hosts now. When it names
the newcomer, the incumbent is retired as `superseded` and the newcomer
inherits its familiar — same terminal, same face. When it names the incumbent,
the newcomer is refused: that is a borrowed pid wearing a real old session id,
the one forgery the ledger check let through. The door re-reads the note for
a moment before deciding, because the note and the hook race.

## Loop 4 — A prompt nobody is waiting behind

**Finding:** Once a permission is granted, no hook fires until the approved
tool finishes. A five-minute build left the familiar at the Permission Gate
saying *Needs you* for five minutes. Escape interrupts a turn without a
`Stop` hook, so *Running command* stood for as long as the session sat there.

**Change:** The note also records `status` — `waiting`, `busy`, `idle` — and
when it changed. The sweep lets a note newer than the session's last event
correct the map: busy after waiting sends the familiar back to the station it
left; idle after work sends it to the Shipping Dock. A hook that arrives later
still wins. `PostToolUse` was considered and rejected: it would add a node
process to every tool call and still only clear the prompt when the tool ends.

## Loop 5 — Helpers wearing the parent's name

**Finding:** Every hook fired inside a subagent carries `agent_id` and
`agent_type`; the session's own hooks carry neither (captured live). The
adapter used `agent_type` as the familiar's name, so the first `SubagentStart`
renamed Moss to "Explore", and the helper's reads walked the parent to the
Research Desk while it was waiting on the Agent tool.

**Change:** Inside a helper the adapter passes only `SubagentStart`,
`SubagentStop` and permission dialogs, and never a name. `TaskCreated` and
`TaskCompleted` are gone from the subscription: they fire for the session's
own task list (`task_id`, `task_subject`, no teammate — verified), and
counting them as helpers showed helpers that did not exist. `PermissionDenied`
is "after auto mode classifier denies a tool call" in Claude Code's own words;
nobody is being asked anything, so it is Trouble, not Needs you.

## Loop 6 — An empty clearing over a busy machine

**Finding:** Restarting the bridge emptied the map until each session's next
hook. Sessions opened before `connect`, or before the bridge, were invisible
until they did something.

**Change:** Every sweep admits any note whose process is running, is Claude
Code, started when the note says, and whose session is not on the map, with
the state the note records. A session that has just ended is not brought back
by the note its exiting process leaves behind for a second; that one was
caught in the live trace, not imagined.

## Rejected

- **`PostToolUse`.** See loop 4.
- **Showing `waitingFor` in the inspector.** The note says what the dialog is
  ("permission prompt", "input needed"). Useful, but it widens the schema for
  a detail the terminal already shows; not this pass.
- **Persisting the bridge's snapshot to disk across restarts.** Discovery from
  the note is the same information from the source itself.
- **Requiring `Content-Type: application/json` on the event endpoint.** Cheap,
  but the process proof already makes a cross-origin POST worthless, and it
  would break a hand-rolled adapter for no trust gained.

## Locked outcome

- One familiar, one running `claude` process whose own note names that
  session. Nothing a sender posts can pick a face, a terminal, a name — or a
  session.
- The map is never emptier than the machine: running sessions are on it within
  two seconds of the bridge starting, before any hook.
- The map is never staler than Claude Code's own record of a session by more
  than two seconds: waiting, busy and idle correct it, and hooks refine it.
- Zero refusals in normal operation. A refusal means a forgery or a bug, and
  the chip is worth reading again.

Verified live at the end of the pass: the bridge restarted on the new code and
listed exactly the sessions `ps` showed; `npm run connect` wrote twelve hooks
into `~/.claude/settings.json` and removed twelve dead ones from the unread
file; a headless session started outside this repo walked Starting → Getting
started → Running → Done and left, with `refusedEvents` at zero.
